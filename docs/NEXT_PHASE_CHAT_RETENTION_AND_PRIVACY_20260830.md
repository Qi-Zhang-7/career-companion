# 下一阶段：会话保留、删除与隐私控制（2026-08-30）

> 本文记录 Companion Chat 数据闭环之后的产品与技术任务。所有实现仍以项目根目录 `PRODUCT_ARCHITECTURE.md` 为准。

## 1. 当前状态

- 每次普通 Chat 会话创建一条 `Conversation`。
- 用户消息和助手消息逐条写入 `ConversationMessage`。
- “结束并总结”会保存 `Conversation.summary`，但不会自动创建长期记忆。
- 当前没有会话删除、自动过期、临时会话和聊天历史总开关。
- 当前适合本地 MVP 验证，不是完整的 C 端隐私方案。

## 2. 下一阶段开发目标

### 第一组：用户可控的会话历史

1. 支持删除单次会话，并二次确认删除影响。（已完成）
2. 支持清空全部聊天历史。
3. 在 Settings 增加“保存聊天历史”开关。
4. 增加“临时对话”：不出现在历史列表、不进入长期记忆候选，并按短周期自动清理。
5. 支持保留期限：建议提供 30 天、90 天、1 年、一直保留。
6. 支持导出聊天记录和会话摘要。

### 第二组：删除生命周期与后台清理

1. 删除操作先记录 `deletedAt`，前端立即不可见。
2. 后台清理任务在承诺期限内物理删除消息和会话。
3. 附件、向量、缓存、搜索索引和备份恢复策略需要与主记录同步。
4. 保存最小化删除审计，只记录对象 ID、时间和结果，不保留已删除正文。
5. 明确安全、欺诈防范或法律义务导致的例外保留，并写入隐私说明。

### 第三组：会话、摘要、记忆三层分离

```text
ConversationMessage：原始聊天正文，可按用户设置删除或过期
Conversation.summary：会话级压缩摘要，随会话一起管理
Memory：跨会话长期使用的结构化信息，必须经过候选与确认流程
```

- 删除会话时，应让用户知道是否存在由该会话确认形成的长期记忆。
- 长期记忆必须保存来源引用，但不能因为原对话删除而继续暴露已删除正文。
- 未经确认的人物性格推测只能保存为候选 Observation / Inference，不能成为 Fact。
- 临时对话不参与记忆提取、成长报告和人物模型更新。

## 3. 推荐交付顺序

```text
单次会话删除（已完成）
  → 清空历史
  → 历史保存开关
  → 临时对话
  → 自动过期与后台清理
  → 数据导出
  → 记忆候选提取与用户确认
```

先完成删除和保留策略，再开始从聊天自动提取长期记忆，避免出现“原聊天删了，但推测仍在人物画像中”的信任问题。

## 4. 推荐存储架构

当前继续使用 PostgreSQL 是合理的，不需要因为聊天消息较多就立即改成 NoSQL。

建议分工：

| 数据 | 推荐存储 |
|---|---|
| 会话、消息、用户、删除状态、保留期限 | PostgreSQL |
| 模型参数、token 使用等变化较多的元数据 | PostgreSQL JSONB 或现有结构化字段 |
| 图片、音频和大型附件 | 对象存储，只在 PostgreSQL 保存引用和权限信息 |
| 长期记忆与人物/事件关系 | PostgreSQL 结构化表 |
| 语义检索向量 | PostgreSQL + pgvector，规模明显增长后再评估独立向量服务 |
| 短期流式状态、限流和临时缓存 | Redis 等缓存服务，后续按需引入 |

当消息量增长后，优先考虑 PostgreSQL 索引、按用户和时间查询、时间分区、冷热归档及连接池；不要仅因为数据量增长就盲目切换数据库类型。

## 5. 验收标准

- 用户能删除一条会话，刷新后不再出现。
- 用户能清空历史，但需要明确确认。
- 关闭历史保存后，新普通消息不会形成可长期浏览的历史。
- 临时对话有明显标识，退出后不可从历史恢复，也不生成 Memory 候选。
- 自动过期任务可重复执行，并且不会误删未到期数据。
- 删除或过期后，关联附件、索引和缓存都有清理结果。
- Memory 页面能说明某条记忆来自何处、是否已确认，并允许独立删除。

## 6. 本阶段暂不包含

- 不接完整 RAG。
- 不为了“像大厂”提前引入 NoSQL 或复杂微服务。
- 不默认使用全部聊天训练模型。
- 不允许模型自行把每条聊天转成长久人物结论。
